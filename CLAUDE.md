# Team coordination platform (Global Shapers AI hackathon)

Hackathon 24-25 Oct 2026. **Deadline: Sunday 25.10. 14:00.** Demo at 15:00 (10 min, on sandbox data).
Team: 1-2 people. Coding with AI is expected. Full challenge text: `docs/BRIEF.md`. Read it once at the start of a session.

## What we are building

One web platform for a 20-person volunteer institute, replacing a Miro board, a manual attendance spreadsheet and untracked work hours. Three areas, each needs a **member view** and an **admin view**, plus a leader-level analytics view across all three:

1. **Tasks.** Projects with tasks, synced two-way with the Google Sheet tasks tab (see "Google Sheets tasks sync"). Tasks are assignable to a person or to a whole department (Departments: Core, Voice, Tech; a member is in any number of them or none, in `member_departments`; a department named like a tier, i.e. Core, is only for that tier: `src/lib/department-rules.ts`). A member sees all of *their* tasks (and their department's) across all projects in one place and can finish, reprioritise, reschedule or hand over a task. Admin sees all projects on one board, adds a project in one step, assigns tasks, sees who finished how many tasks and when. Keep task history (the Miro problem: "when a card moves, its history is gone"). Tasks are imported read-only from a Google Sheet (see "Google Sheets task import").
2. **Hours.** Member logs hours in seconds and sees progress against their tier's weekly commitment. Admin sees who is behind this week and any member's history.
3. **Meetings** (UI name; routes `/meetings`, `/admin/meetings`; this area tracks meeting attendance). Member clocks in to a meeting in seconds and sees their history (present / remote / excused / unexcused). Admin records attendance for any meeting with minimal effort and sees everyone across all six meeting series.
4. **Analytics (admin).** Hours, meeting attendance and tasks per member, across tiers, series and time. Must be useful to a leader: who is active, who is drifting, how the organisation is doing.

## How we are judged (decide trade-offs by this)

- Usefulness 40%: would the institute use it next week as it is?
- Completeness 25%: do all three areas work for members AND admins on the sandbox data?
- Quality 20%: fast, clear, pleasant for someone who opens it twice a week.
- Rebuildability 15%: can they redeploy from the repo + one-page infra description without us?

Extras (gamification, Slack, Jarvis agent) count **only after all three areas work**. They never replace a missing area. Do not start extras early.

## Hard constraints

- Meetings live in Google Calendar. **Read only. Never create or edit events.**
- Slack: the core platform **writes nothing to Slack**. Slack posting/reading is an extra only.
- AI features only where they genuinely make a task easier. Unwelcome where they do not.
- Admin-only data (e.g. Slack activity signal) is never shown to members.
- No real people or data. The sandbox domain `sandbox.example` does not exist.
- Never commit secrets. Keep a `.env.example` with variable names only.

## Calendar access and meetings

Meetings are read from the Google Calendar's iCal (.ics) export, never written. Code: `src/lib/meetings/` (`ics.ts` parses with ical.js, `import.ts` saves, `rules.ts` attendance/reminder rules, `reminders.ts` sends; `ics.test.ts` and `rules.test.ts`), pages `src/app/(app)/meetings/` and `src/app/(app)/admin/meetings/`.

- Sources: with `MEETINGS_ICS_URL` (the calendar's "Secret address in iCal format") meetings are **pulled automatically**: pages that show meetings (`/meetings`, `/meetings/[id]`, `/dashboard`, `/admin/meetings`) call `syncCalendarInBackground()` (`auto-sync.ts`), which after the response pulls the calendar when the last attempt is older than 15 minutes (`CALENDAR_SYNC_MINUTES`; failed attempts count too, so a broken address is not hammered); the scheduled job does the same; admins have "Sync now". No scheduler is needed for this. Without the URL, admins upload an .ics file (Google Calendar → Settings → Import & export → Export). The seed imports `data/meetings.ics`. Cached in `meetings` so the app is fast; Google stays the source of truth.
- Description: `meetings.description` holds the event's DESCRIPTION for people (`displayDescription()` in `ics.ts`: iCal escapes undone, line breaks kept, HTML stripped to text, links keep their address, the machine lines `Series:`/`Members:` removed; null if nothing is left). Updated on every re-import when it changed. Shown on the meeting page and as a collapsible line in the list via `LinkifiedText` (plain text, URLs as links with `target=_blank rel=noopener noreferrer`, never raw HTML).
- A meeting whose UID is new but whose title and start match an existing meeting not in the import is the same meeting (Google gives events new UIDs when an .ics is imported into it): its UID is updated and its attendance kept (`relinked` in the report).
- Parsing: UID (recurring occurrences `UID#<start UTC>`, expanded from 6 months back to 1 year ahead), TZID/VTIMEZONE (unknown zones read as Europe/Ljubljana), EXDATE, moved occurrences, STATUS:CANCELLED. Series = `Series:` line in DESCRIPTION, else CATEGORIES, else title. Invitees = `Members:` line in DESCRIPTION plus ATTENDEE emails, matched to members by email (unknown emails reported).
- Re-import is idempotent (matched by UID; invites replaced; attendance untouched; a moved meeting gets its reminders again). A whole-calendar import (URL, or file with the box ticked) marks future meetings missing from it `removed` (hidden, kept).
- Attendance (`attendance`): `present` / `remote` by the member during check-in (15 min before start to 15 min after end); `excused` with a reason until 24 h after the end; no record once check-in has closed = **unexcused** (derived, not stored). Admins set any state any time, "mark the others present", and their record locks it for the member. `attendance.xlsx` is seeded (`source = seed`).
- Reminders: by email, default 1 day and 10 minutes before; each member picks from 1 week, 3 days, 1 day, 3 h, 1 h, 30 min, 10 min, or turns them off (`reminder_settings`). The scheduled job `GET /api/cron/reminders` (header `Authorization: Bearer CRON_SECRET`, every 5 min from any scheduler) sends what is due; `meeting_reminders` makes it idempotent; no reminder after the start or for an excused meeting. Locally: `npm run reminders -- --watch`.
- Email: SMTP via nodemailer (`src/lib/email.ts`), every network step with a 10 s timeout (`SMTP_TIMEOUT_MS` to change). Reminder jobs (`meetings/reminders.ts`, `tasks/reminders.ts`, shared `lib/reminder-delivery.ts`) never do network I/O inside a database transaction: a short transaction takes the advisory lock, finds what is due and claims it (reminder rows inserted `pending`), then after the commit the emails go out (max 50 per run, a time budget, 4 at a time), then each row becomes `sent` or `failed` (error text in `email_log`); one failure does not stop the rest; unsent claims are given back; a `pending` row older than 10 minutes (a run that died) is retried. The cron route has a 40 s budget inside `maxDuration = 60`, does nothing if another run holds the lock, and pulls the calendar after the response. Admins can send themselves (or `MAIL_REDIRECT_TO`) a test email from `/admin/meetings`. Without `SMTP_HOST` nothing is sent, emails are only recorded in `email_log` (shown on `/admin/meetings`). `MAIL_REDIRECT_TO` sends every email to one address (demo/testing). Sandbox addresses do not exist, so never send to them for real.

## Projects (`/projects`)

- `projects` (name unique, optional description); `tasks.project_id` (at most one project, `set null` on delete). App-only: the sheet has no project column and the sync never touches `project_id`.
- `/projects` (everyone, "Projects" in the menu; `/admin/tasks` redirects here): every project as a collapsed `<details>` row showing only how many tasks are unfinished; opening it lists all its tasks (unfinished first by priority, then due date; done last; `src/lib/projects/overview.ts`, tested) with "+ Add a task" (`/tasks/new?project=<id>`). Tasks without a project come last as "No project". `?open=<id>` opens one.
- Admins add a project in one step (name + optional description), rename it, and delete it only while it has no tasks. Anyone who can edit a task sets its project in the task form; changes go to `task_events`.
- Seed: the team's seven running projects with 4-5 **placeholder** tasks each (for a person, a department or nobody; a few urgent or low; mixed statuses and due dates; history says "Placeholder task (sample data)"), from `scripts/team-projects.ts`, also on its own with `npm run seed:projects`. Idempotent: projects by name, a project that has tasks gets none; the old placeholder projects are removed while they have no tasks. The placeholder tasks are app tasks, so they sync to the sheet of the database they are created in.

## Google Sheets tasks sync (two-way)

Via the Sheets API with a service account (scope `spreadsheets`, account shared as **Editor**). Code: `src/lib/google/sheets.ts` (client, one `SheetTab` per tab, exact Google errors, `fake-sheets.ts` for tests), `src/lib/tasks/` (`sheet-mapping.ts` maps, `sheet-sync.ts` syncs, tests in `sheet-sync.test.ts`).

- **Scope:** only the tab `GOOGLE_SHEET_TASKS_TAB` (default `List1`) is opened. Never the Users tab or List4. Never read or write the Geslo column: we read row 1 (header names) and then only our seven columns, and write only those cells.
- Columns by header (trimmed, case/diacritic-insensitive): `task` → title, `status` → todo/in_progress/verification/done (English + Slovenian variants; unknown → todo, reported; written as "to do"/"in progress"/"verifikacija"/"done"), `nosilec` → a department if it names one (e.g. "Tech", "oddelek Tech"), else the assignee by first name, full name, email or email prefix (only on exactly one match; written in the style the sheet already uses). Assignee and department share the cell, so the merge treats them as one value (`UNITS` in `sheet-sync.ts`); the DB check `tasks_one_owner` forbids both, `tip taska` → type (one of `TASK_TYPES` in `src/lib/tasks/constants.ts` if it matches ignoring case, else kept as typed; the app's form offers only `TASK_TYPES`, a task keeps a sheet-only type when edited), `deadline` → due date (dd.mm.yyyy, d.m. = next upcoming, yyyy-mm-dd, Sheets serials; Europe/Ljubljana; written as dd.mm.yyyy), `priority` (also `prioriteta`) → urgent/medium/low (English + Slovenian words, `mapPriority`; written as "urgent"/"medium"/"low"; the column is added after the last header if missing; an empty or unknown cell is not a sheet change: the app's priority is written into it, unknown words are reported), `id` → the task key.
- **Identity:** column `id` (added after the last header if missing) holds the task's `sheet_key` (`t-` + 10 hex). Sorting or re-running never duplicates. Rows without a key are matched once by the legacy key (normalised title + occurrence, `tasks.source_key`), else created, and get a key written. Keys are saved in the DB before the sheet is written. A copied row with a repeated key becomes a new task. A deleted row flags the task "no longer in sheet" (never deleted, never re-added).
- **Conflict rule:** per-field three-way merge against `tasks.sheet_snapshot` (what the sheet held after the last sync). Sheet-only change → app takes it; app-only change → written to the sheet; both changed → **the app wins** (the sheet has no edit times), the overwritten sheet value goes to `task_events` (kind `conflict`) and the admin report. An unreadable deadline never wipes an existing due date.
- **When:** in the background via `after()` on login and on the tasks pages if the last sync finished over 60 s ago, and right after any task edit. A lease in `sync_state` (name `tasks_sheet`) guarantees one sync at a time across instances. "Sync now" is for every member, and so is the reason a sync failed (a task not yet in the sheet says so, with the error); the detailed report (`task_syncs`: raw values, skipped rows) is admin-only.
- **Done is reversible:** one tick/untick control (`DoneToggle`) on the task list, task page and the dashboard's open tasks, plus an 8-second Undo toast. Ticking stores `tasks.completed_at` and `status_before_done`; unticking restores that status (else "in progress" if it was ever started, else "to do"), clears `completed_at` and records a `reopened` history row. All status changes (app, edit form, sheet sync, Take it) go through `src/lib/tasks/done.ts`/`changes.ts`. Counts use the current `completed_at`, so done → reopened → done counts once. Tasks imported already done from the sheet have no known completion time and are not counted.
- **Permissions:** any member creates tasks (on `/tasks` or the dashboard) (assignee defaults to themselves) and edits/hands over/finishes tasks assigned to them, delegated to one of their departments, or created by them; anyone in the department can **Take it** (it becomes theirs); admins edit all and manage departments on `/admin/departments` (tick a member's departments on the member page; Core is ticked/unticked with the Core tier). Every change goes to `task_events`.
- Check the connection for real: `npm run sheets:check` (add `-- --hours-entry <id>` to send one finished time entry and confirm its row).

## Task priority and deadline reminders

- `tasks.priority`: `urgent` / `medium` (default) / `low` (`TASK_PRIORITIES` in `src/lib/tasks/constants.ts`, most pressing first). Set in the task form by anyone who can edit the task (history as usual); `PriorityBadge` everywhere (only Urgent stands out). Lists (`/tasks`, `/projects`) sort open tasks by priority, then due date, then title, finished last (`priorityOrder` in `src/lib/tasks/queries.ts`, `sortTasks` in `src/lib/projects/overview.ts`); `/tasks` filters by priority. Synced with the sheet's `priority` column (see above).
- Deadline reminders by email (`src/lib/tasks/reminders.ts` sends, `reminder-rules.ts` pure rules tested in `reminder-rules.test.ts`, job tested in `reminders.test.ts`): sent at 08:00 Ljubljana, N days before the due date; each member picks 3 days / 1 day (default) / on the due day, or off, at the bottom of `/tasks` (`reminder_settings.task_email_enabled`, `task_days_before`). To the assignee, or every active member of the department for a department task. Only open tasks with a due date that are not deleted, not unconfirmed AI tasks and still in the sheet. Missed reminders (a due date set late) go out together in one email, never after the due day. `task_reminders` (task, member, due date, days) makes it idempotent; a rescheduled task is reminded again. Same scheduled job and email setup as meeting reminders (`/api/cron/reminders`, `npm run reminders`).

## Work hours (timer) and the "Ure dela" tab

Clockify-style: Start/Stop on `/hours` and the dashboard, plus manual entries. Code: `src/lib/hours/` (`time.ts` pure helpers with tests, `queries.ts`, `sheet-sync.ts`), pages in `src/app/(app)/hours/` and `src/app/(app)/admin/hours/`.

- **The database is the source of truth** (`time_entries`, `ended_at` null = timer running, one running timer per member by a partial unique index). Weeks run Monday-Sunday in Europe/Ljubljana; totals clip entries to the week.
- **The sheet is a one-way mirror.** When a timer stops (or an entry is added/changed/deleted) the entry is marked `sheet_status = pending` and `after()` runs `syncHoursSheet()`: it writes the row `oseba (full name) | dan začetka | ura začetka | dan konca | ura konca | id` to tab `GOOGLE_SHEET_HOURS_TAB` (default `Ure dela`), updating the row whose column F has the entry id or appending one, and removing the row of a deleted entry. Idempotent, one run at a time (advisory lock). Failures stay pending; admins retry on `/admin/hours`. The app never reads hours back from the sheet: corrections are made in the app.
- Writing needs the service account as **Editor**. `sheet-sync.ts` only opens the hours tab; it creates the tab with its header if it is missing. Failures are stored (`time_entries.sheet_error`, `sync_state` row `hours_sheet`): members see "not synced to the sheet" on the entry, admins see the exact last error and a retry button on `/admin/hours`. The Stop path is in `src/lib/hours/timer.ts` (tested in `stop-and-sheet.test.ts`).
- Rules: timers under 1 minute are discarded; a timer running over 12 h asks for the real end time; entries are 1 min to 24 h and may not overlap. Members add and change their own entries from this week; admins change any entry and add hours for anyone. Seed entries (`source = seed`, from `hours.xlsx`, five per week Mon-Fri) are never written to the sheet.
- **Work location** (`time_entries.location`: `office` | `home`, null = "unspecified"). Start and manual entry ask for it with a two-button toggle defaulting to the member's last choice (`lastLocation()`, else office). Entries from before (seeded, older) stay null and show as "Unspecified": never guess. Shown on entry rows, weekly totals (`locationTotals()` in `location.ts`), admin history and two analytics charts. Not in the "Ure dela" sheet: that sync is positional (A:F, ids in F), not by header, so a new column is left out on purpose.

## Meeting notes → AI tasks

- Meeting invitees and admins add notes on the meeting page (paste, or a .txt/.md/.vtt/.srt file; max 100,000 characters; subtitle timestamps stripped). Stored in `meeting_notes`, readable only by that meeting's invitees and admins.
- "Create tasks from notes" (`src/lib/ai/meeting-tasks.ts` + `meeting-tasks-run.ts`): Anthropic API server-side only, model `ANTHROPIC_MODEL` (default `claude-sonnet-5-5`), structured outputs (`output_config.format`, zod) with server-side refusal fallbacks. The prompt gives the meeting's invitees (name + email) and date; notes are fenced in `<meeting_notes>` and treated as untrusted data. Every item is re-validated: assignee matched to an invitee by email/name (unknown → unassigned, never an id from the model), due date valid and near the meeting, type from `TASK_TYPES`, invalid items dropped. Hidden (with an admin note) when `ANTHROPIC_API_KEY` is missing.
- Meeting recorder (admins only; `src/components/recorder/`, `src/lib/recordings/`, actions in `src/app/(app)/meetings/recording-actions.ts`): `RecorderProvider` in the app layout (admins only) owns mic → AudioWorklet (`public/recorder-worklet.js`, mono PCM) → Web Worker (`mp3-worker.ts` + `SegmentEncoder`, lamejs, 16 kHz mono 32 kbps, 10-min segments) → IndexedDB (`idb.ts`) → signed upload URL → PUT to Supabase Storage → `confirmSegment` (checks the object's size; unique (recording_id, index) makes retries idempotent). Audio never passes through our functions. Interrupted recordings (IndexedDB session still "recording") are offered "Finish uploading". Playback/download: signed links, MP3 parts joined in the browser (`mp3-join.ts`). Access: admins create/transcribe/delete; admins + the meeting's invitees play and read (`canListen`). Transcription: `transcribe.ts` (OpenAI-compatible, Groq by default; a 429 is a `RateLimitError`: the run stops, the parts not yet done are marked failed with a retry message, finished parts are kept), run by `runTranscription` in `after()` with a lease and a time budget; the progress poll restarts it; failed parts retried alone; joined with `[hh:mm:ss]`. "Save as meeting notes" is the only way a transcript reaches "Create tasks from notes". Tests: `recordings.test.ts` (fake store, mocked provider), `segment-encoder.test.ts`, `join.test.ts`, `transcribe.test.ts`.
- "Ask about a meeting" (`/meetings/ask`; `src/lib/ai/meeting-qa.ts` pure + `meeting-qa-run.ts`): a member picks a meeting (or a date: picked, or parsed from the question in English/Slovenian, e.g. "14 October", "14. oktobra"; several meetings with notes that day → "which one?"). Only that meeting's invitees and admins (`canUseMeetingNotes`); others get the same refusal whether or not the meeting exists. The meeting's notes (newest first, capped at `QA_NOTES_MAX_CHARS`) are fenced in `<meeting_notes>`, the question in `<question>`; the answer is in the question's language, with quotes. Every quote is checked against the notes; an answer without a real quote is shown as "the notes don't say". Rate limit `AI_QUESTIONS_PER_HOUR` per member via `ai_questions` (stores usage only, never the question or answer). Hidden (404 and no links) without `ANTHROPIC_API_KEY`.
- Idempotent: identical notes reuse the stored items of the earlier run (`ai_task_runs`, no second API call); every created item is recorded per meeting by normalised title + assignee (`ai_task_items`), so reruns never duplicate and a deleted AI task is never recreated. Rate limit: 5 API runs per member per hour.
- AI tasks: `created_by_ai`, `source_meeting_id`, `source_quote`, `ai_model`, `triggered_by_id` (created_by_id stays null), `ai_confirmed_at`. Badge "AI" / "AI, confirmed" everywhere; the assignee reviews (Confirm / edit / reassign / Delete). Deletion is soft (`deleted_at`); the sheet sync removes the row. Unconfirmed AI tasks are not counted in a member's numbers. They sync to the sheet like any task; the sheet carries no AI marker.

## Admin analytics (`/admin/analytics`)

- Data: `src/lib/analytics/load.ts` (rows, server-only) + `compute.ts` (pure, tested in `compute.test.ts`). No API endpoint: the admin-only page computes everything on the server; middleware returns 403 to members.
- Same rules as the rest of the app: `weekPace()` for on track (pro-rated), `effectiveState()` (unanswered past meeting = unexcused) and `attendanceSummary()` for rates. Unconfirmed AI tasks and deleted tasks are never counted.
- Filters (URL): tier, meeting series, range (4 weeks / 8 weeks / all, max 26). Drifting = under 50% of target in 2+ of the last 4 full weeks, or 2+ unexcused in the last 6 meetings.
- Charts are plain SVG (`src/components/charts.tsx`), colours from `--viz-*` tokens validated for colour-blind safety in both themes; every chart has a title, a text summary, a tooltip on hover/focus and a table view.

## Absence notices, general tasks, notifications (member feedback, Taj)

All rules are in `src/lib/absence-rules.ts` (change them there). ASSUMPTION: "general task" means a standing task anyone can help with, which a member picks after missing a meeting; the reading comes from a short note.
- **72-hour notice:** an excuse sent at least `ABSENCE_NOTICE_HOURS` (72 real hours, Europe/Ljubljana for display) before the start counts as excused. Later: `attendance.late_notice`; it counts as unexcused (`effectiveState()` with the late fields, used by every count incl. analytics) until an admin accepts it (`late_decision`). The excuse form shows the rule, the deadline and the time left; admins decide on the meeting page and see pending ones on `/admin/meetings`.
- **General tasks:** `tasks.kind = 'general'` (+ `description`), admin-managed on the "General tasks" tab of `/tasks`. Never done: `assertMayChangeStatus()` in `lib/tasks/changes.ts` rejects it on the server, no done control is shown, they are never written to the sheet and a "done" from the sheet is ignored.
- **Missed meeting:** when an admin records an absence that `GENERAL_TASK_AFTER` lists (by default unexcused, or a late notice not accepted), `followUpAbsence()` creates a `general_task_requests` row and a notification; the member picks one general task in one tap. Changing the absence before a pick cancels the request. Admins see "Still to pick a general task". Who picked what is shown by name to admins only.
- **Notifications:** `notifications` table, bell with unread count in the header, `/notifications`. Every query is scoped to the signed-in member; never put admin-only information into a notification.

## Slack meeting announcements (extra, `/admin/slack`)

- Only with `SLACK_BOT_TOKEN` (bot scopes `chat:write`, `channels:read`, `channels:join`, `users:read`, `users:read.email`); without it nothing touches Slack and Admin → Slack shows the setup steps. The rest of the platform still writes nothing to Slack.
- Code: `src/lib/slack/` (`client.ts` plain-fetch Web API client + `describeSlackError`, `fake-slack.ts` for tests, `announce-rules.ts` pure text and decisions tested in `announce-rules.test.ts`, `announcements.ts` the sync tested in `announcements.test.ts`, `workspace.ts` channels/people for the admin page), page `src/app/(app)/admin/slack/`.
- Each meeting gets two announcements, 3 days and 1 day before (`ANNOUNCEMENT_KINDS`), as Slack **scheduled messages** (`chat.scheduleMessage`, max 120 days ahead), so no scheduler is needed at posting time. `slack_announcements` (meeting, kind) keeps status scheduled/posted/cancelled/failed, the scheduled message id and a content hash. A run (`runSlackSync`, lease `slack_announcements` in `sync_state`, at most every 5 min unless forced) schedules new ones, reschedules when the time, channel or text changed (meeting moved, invitees, mentions), deletes them for cancelled/removed meetings, marks them posted once their time has passed, and posts a missed one right away (one message per meeting; not within an hour of the start). Runs after the calendar sync (`syncCalendarInBackground`), from `/api/cron/reminders`, `npm run reminders`, and on save / "Sync with Slack now".
- Channel per series in `slack_channels` (series `*` = default; no channel → not announced, listed as such). The app joins public channels itself (`conversations.join`); private channels need `/invite`.
- Text: title, series, when (as seen at posting time), day and time in Ljubljana, location, invitees on Slack as mentions (+ "and N more"), link to the meeting page. Members are matched by email (`users.lookupByEmail`, cached in `slack_members`, retried after 6 h) or picked by an admin (`manual`), since sandbox emails do not exist in a real workspace.
- One environment per workspace: a local copy with the same token would announce every meeting a second time.

## Performance rules (details and numbers: `docs/PERFORMANCE.md`)

The database is reached through Supabase's transaction pooler, so statements are not prepared (`prepare: false` in `src/db/index.ts`). Consequence: every query that has parameters costs **two round trips** (the driver first asks for the parameter types), so a page's time is about *(number of sequential waves of queries) x 2 x the round-trip time to the database*. Count waves, not queries.
- A page is one session lookup (`requireMember()`, a single parameter-free statement that also returns the unread-notification count; the layout and the page share it) followed by **one** parallel wave of queries. Never `await` one query after another when they are independent; never query inside a loop (N+1); use joins, window counts or `inArray`.
- Queries that do not depend on who is asking (admin pages, `[id]` detail pages) start in the same `Promise.all` as `requireAdmin()` / `requireMember()`. Nothing from them is rendered before the access check.
- Never do slow work while rendering: Google Sheets and calendar syncs, email, AI calls run in `after()` or the cron job (or behind a button the user pressed); pages show the last known state.
- Analytics add up in SQL (`src/lib/analytics/weekly-hours.ts`, tested against the JavaScript way), for the weeks shown only. Do not load every time entry or task into JavaScript.
- Every section has a `loading.tsx` (skeleton) so the page frame appears at once and link prefetching works. A new filter on a growing table gets an index in a migration.
- The pool is 10 connections per instance; a page should not need more parallel queries than that.

## Theme (light / dark)

- All colours are design tokens (CSS variables) in `src/app/globals.css`, light values on `:root`, dark on `[data-theme="dark"]`, exposed to Tailwind via `@theme inline` (`bg-surface`, `text-muted`, `border-line`, `bg-success-bg text-success`, ...). Never use raw palette classes (`bg-white`, `text-slate-600`, `bg-red-50`); add a token instead. Every text/background token pair passes WCAG AA (4.5:1) in both themes.
- Choice System (default) / Light / Dark: `ThemeSwitch` in the header and on the login page, stored in the `theme` cookie. The root layout renders `data-theme` for an explicit choice; `THEME_SCRIPT` (`src/lib/theme.ts`, inline in `<head>`) resolves "system" from `prefers-color-scheme` before first paint and follows it live. `color-scheme` is set in CSS and the viewport meta so native controls match. Tailwind 4 `dark:` variant: `@custom-variant dark` on `[data-theme=dark]`.
